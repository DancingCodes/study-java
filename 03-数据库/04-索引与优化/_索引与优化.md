# 索引与优化

## 一、什么是索引

索引就像**书的目录**。没有目录，找内容要一页一页翻（全表扫描）；有了目录，直接翻到对应页码（索引查找），速度快很多。

- 没索引：`SELECT * FROM employee WHERE name = '张三'` → 逐行扫描所有数据
- 有索引：同样的查询 → 通过索引直接定位到张三那行

**代价**：索引会占用额外存储空间，而且插入/更新/删除时需要同步维护索引，所以不是越多越好。

## 二、索引类型

### 2.1 按功能分类

| 类型 | 说明 | 关键字 |
|------|------|--------|
| 主键索引 | 主键自动创建，唯一且不为空 | PRIMARY KEY |
| 唯一索引 | 值不能重复（可以有一个 NULL） | UNIQUE |
| 普通索引 | 最基本的索引，没有限制 | INDEX |
| 全文索引 | 用于全文搜索（用得少，一般用 ES 替代） | FULLTEXT |

### 2.2 按结构分类

MySQL 默认使用 **B+ 树索引**，了解即可：
- 数据存在叶子节点，叶子节点之间用链表连接
- 查询效率稳定，无论数据量多大，查询次数都是树的高度（通常 3-4 层）
- 适合范围查询（BETWEEN、>、<）和排序（ORDER BY）

## 三、索引操作

### 3.1 创建索引

```sql
-- 建表时创建
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    phone VARCHAR(20),
    UNIQUE INDEX idx_email (email),       -- 唯一索引
    INDEX idx_phone (phone)               -- 普通索引
);

-- 给已有表添加索引
CREATE INDEX idx_name ON employee(name);
CREATE UNIQUE INDEX idx_email ON user(email);

-- 用 ALTER TABLE 添加
ALTER TABLE employee ADD INDEX idx_department (department);
```

### 3.2 查看索引

```sql
SHOW INDEX FROM employee;
```

### 3.3 删除索引

```sql
DROP INDEX idx_name ON employee;
```

### 3.4 复合索引（联合索引）

一个索引包含多个字段，适合经常一起查询的字段组合。

```sql
-- 经常按部门+薪资查询，建一个复合索引
CREATE INDEX idx_dept_salary ON employee(department, salary);
```

**最左前缀原则**：复合索引 `(department, salary)` 能加速以下查询：
```sql
-- ✅ 能用到索引
WHERE department = '技术部'
WHERE department = '技术部' AND salary > 15000

-- ❌ 用不到索引（跳过了最左边的 department）
WHERE salary > 15000
```

就像查字典：先按拼音首字母找，再按第二个字母找。你不能跳过首字母直接按第二个字母查。

## 四、EXPLAIN — 分析查询

EXPLAIN 是查询优化的核心工具，在 SELECT 前加 `EXPLAIN` 就能看到 MySQL 怎么执行这条查询。

```sql
EXPLAIN SELECT * FROM employee WHERE name = '张三';
```

### 4.1 重点关注的字段

| 字段 | 含义 | 关注点 |
|------|------|--------|
| **type** | 访问类型 | 越靠左越好：const > eq_ref > ref > range > index > **ALL** |
| **key** | 实际使用的索引 | NULL 表示没用到索引 |
| **rows** | 预估扫描行数 | 越小越好 |
| **Extra** | 额外信息 | 注意 Using filesort、Using temporary |

### 4.2 type 详解

| type | 含义 | 举例 |
|------|------|------|
| const | 主键或唯一索引精确查找 | WHERE id = 1 |
| eq_ref | JOIN 中主键/唯一索引匹配 | 多表 JOIN |
| ref | 普通索引等值查找 | WHERE department = '技术部' |
| range | 索引范围查找 | WHERE salary > 15000 |
| index | 扫描整个索引树 | 覆盖索引场景 |
| **ALL** | **全表扫描（最差！）** | 没有可用索引 |

看到 `ALL` 就要想办法优化（加索引或改写查询）。

### 4.3 Extra 中的警告

- **Using filesort** — 额外排序，没用到索引的排序，数据量大时很慢
- **Using temporary** — 使用临时表，通常出现在 GROUP BY、DISTINCT 中
- **Using index** — 好事！覆盖索引，数据直接从索引获取，不需要回表

## 五、慢查询排查

### 5.1 开启慢查询日志

```sql
-- 查看是否开启
SHOW VARIABLES LIKE 'slow_query_log';

-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;

-- 设置慢查询阈值（超过 1 秒的记录下来）
SET GLOBAL long_query_time = 1;

-- 查看慢查询日志文件位置
SHOW VARIABLES LIKE 'slow_query_log_file';
```

### 5.2 常见慢查询原因及优化

| 原因 | 解决方案 |
|------|----------|
| 没有索引，全表扫描 | 加合适的索引 |
| 索引没用上 | 检查查询条件是否命中索引（EXPLAIN 看 key） |
| SELECT * 查了不需要的字段 | 只查需要的字段 |
| LIKE '%xxx' 左模糊 | 改为右模糊 'xxx%' 或用全文搜索 |
| 数据量太大没分页 | 加 LIMIT 分页 |
| JOIN 太多表 | 减少 JOIN 或拆分查询 |

### 5.3 索引失效的场景

```sql
-- ❌ 对字段使用函数
WHERE YEAR(hire_date) = 2024     -- 索引失效
WHERE hire_date >= '2024-01-01' AND hire_date < '2025-01-01'  -- ✅ 改为范围

-- ❌ 左模糊
WHERE name LIKE '%三'            -- 索引失效
WHERE name LIKE '张%'            -- ✅ 右模糊能用索引

-- ❌ 类型不匹配（隐式转换）
WHERE phone = 13800138000        -- phone 是 VARCHAR，传了数字，索引失效
WHERE phone = '13800138000'      -- ✅ 类型匹配

-- ❌ OR 条件中有一个没索引
WHERE name = '张三' OR age = 20  -- 如果 age 没索引，整个都不走索引
```

## 六、什么时候该加索引

**该加的**：
- WHERE 条件经常用到的字段
- JOIN 的关联字段（ON 后面的）
- ORDER BY、GROUP BY 的字段
- 经常查但很少改的字段

**不该加的**：
- 数据量很小的表（几百行以内全表扫描也很快）
- 频繁增删改的字段（维护索引的开销大）
- 值重复率很高的字段（如性别，只有男/女，索引没意义）
