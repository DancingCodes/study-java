# 数据库设计

## 一、为什么要学数据库设计

写代码之前先设计表结构，就像盖房子之前先画图纸。表设计得好，后续开发顺畅；设计得差，后面改起来痛苦。

## 二、表关系

实际业务中，表和表之间存在三种关系：

### 2.1 一对一（1:1）

一个用户对应一份详细资料。可以放一张表，也可以拆成两张表（主表存常用字段，副表存不常用的大字段）。

```
user 表：id, username, password
user_detail 表：id, user_id, address, bio, avatar
```

### 2.2 一对多（1:N）

**最常见**的关系。一个部门有多个员工，一个用户有多个订单。

```
department 表：id, dept_name
employee 表：id, name, department_id  ← 外键放在"多"的一方
```

**关键**：外键字段放在**"多"的那一方**。一个部门对应多个员工，所以 `department_id` 放在 employee 表里。

### 2.3 多对多（M:N）

一个学生可以选多门课，一门课有多个学生。需要一张**中间表**来关联。

```
student 表：id, name
course 表：id, course_name
student_course 表：id, student_id, course_id  ← 中间表
```

## 三、三范式

三范式是数据库设计的基本规范，目的是**减少数据冗余，避免更新异常**。

### 第一范式（1NF）：字段不可再分

每个字段只存一个值，不能存多个值或嵌套结构。

```
❌ 违反 1NF：
| name | phone              |
|------|--------------------|  
| 张三 | 138xxx, 139xxx     |  ← 一个字段存了两个手机号

✅ 符合 1NF：
| name | phone1   | phone2   |
|------|----------|----------|
| 张三 | 138xxx   | 139xxx   |

或者拆成单独的 phone 表（更推荐）
```

### 第二范式（2NF）：消除部分依赖

非主键字段必须**完全依赖于主键**，不能只依赖主键的一部分。

```
❌ 违反 2NF（联合主键 student_id + course_id）：
| student_id | course_id | student_name | score |

student_name 只依赖 student_id，不依赖 course_id → 部分依赖

✅ 符合 2NF：拆成两张表
student 表：student_id, student_name
score 表：student_id, course_id, score
```

### 第三范式（3NF）：消除传递依赖

非主键字段不能依赖另一个非主键字段。

```
❌ 违反 3NF：
| employee_id | department_id | department_name |

department_name 依赖 department_id，而不是直接依赖 employee_id → 传递依赖

✅ 符合 3NF：拆表
employee 表：employee_id, department_id
department 表：department_id, department_name
```

### 三范式总结

| 范式 | 核心 | 通俗理解 |
|------|------|----------|
| 1NF | 字段不可再分 | 一个格子只放一个值 |
| 2NF | 消除部分依赖 | 每列都和完整主键相关 |
| 3NF | 消除传递依赖 | 非主键列之间不能互相依赖 |

**实际开发中**：大部分满足 3NF 就够了。有时为了查询性能会**适当冗余**（反范式），比如订单表里存一份商品名，避免每次都 JOIN 商品表。

## 四、ER 图（实体关系图）

ER 图是数据库设计的可视化工具，画清楚了再建表。

基本元素：
- **矩形** — 实体（表），如：用户、订单、商品
- **椭圆** — 属性（字段），如：用户名、手机号
- **菱形** — 关系，如：下单、选课
- **连线** — 标注 1:1、1:N、M:N

简化画法（实际开发常用）：
```
┌──────────┐       1:N      ┌──────────┐
│  user    │───────────────→│  order   │
├──────────┤                ├──────────┤
│ id       │                │ id       │
│ username │                │ user_id  │
│ phone    │                │ amount   │
│ password │                │ status   │
└──────────┘                └──────────┘
```

## 五、建表规范（企业常用）

### 5.1 命名规范

- 表名、字段名用**小写 + 下划线**：`user_order`、`create_time`
- 表名用**名词单数**：`user` 而不是 `users`
- 字段名要有意义：`status` 而不是 `s`
- 布尔字段用 `is_` 开头：`is_deleted`、`is_active`

### 5.2 每张表必备字段

```sql
id          BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
create_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
is_deleted  TINYINT DEFAULT 0 COMMENT '逻辑删除 0-未删除 1-已删除'
```

- `id` — 主键，用 BIGINT
- `create_time` — 记录创建时间
- `update_time` — 自动更新修改时间（`ON UPDATE CURRENT_TIMESTAMP`）
- `is_deleted` — 逻辑删除，不真正删数据，标记为已删除

### 5.3 逻辑删除 vs 物理删除

```sql
-- 物理删除：真正删掉数据（不可恢复）
DELETE FROM user WHERE id = 1;

-- 逻辑删除：只是标记（数据还在，可恢复）
UPDATE user SET is_deleted = 1 WHERE id = 1;

-- 查询时排除已删除的
SELECT * FROM user WHERE is_deleted = 0;
```

企业项目**几乎都用逻辑删除**，防止误删数据。

- 用户可以注册登录（用户名、密码、邮箱、头像）

1. 分析有哪些实体（表）
2. 分析表之间的关系（1:1、1:N、M:N）
3. 写出完整的 CREATE TABLE 语句（包含必备字段 id、create_time、update_time、is_deleted）
