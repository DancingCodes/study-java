# 认证授权

## 一、认证 vs 授权

这两个概念经常搞混，先理清：

| | 认证（Authentication） | 授权（Authorization） |
|---|---|---|
| 问题 | 你是谁？ | 你能干什么？ |
| 类比 | 刷工牌进大楼 | 你的工牌能进哪些楼层 |
| 实现 | 登录（用户名+密码、Token） | 角色/权限校验 |
| 顺序 | 先认证 | 后授权 |

- **认证**：验证用户身份（登录）
- **授权**：验证用户是否有权限执行某个操作（如管理员才能删除商品）

## 二、传统 Session 认证 vs JWT 认证

### 2.1 Session 认证（传统方式）

```
1. 用户登录 → 服务器创建 Session，存在服务器内存
2. 服务器返回 SessionID → 浏览器存在 Cookie
3. 后续请求自动带 Cookie → 服务器根据 SessionID 找到 Session
```

**问题**：
- Session 存在服务器内存，用户多了内存扛不住
- 多台服务器时 Session 不共享（A 服务器的 Session，B 服务器不认识）
- 前后端分离 + 移动端不方便用 Cookie

### 2.2 JWT 认证（主流方式）

JWT（JSON Web Token）= 一个加密的字符串，包含用户信息。

```
1. 用户登录 → 服务器生成 JWT Token 返回给前端
2. 前端保存 Token（localStorage）
3. 后续请求在 Header 中带上 Token：Authorization: Bearer xxxxx
4. 服务器解析 Token 验证身份 → 不需要存 Session
```

**优势**：
- **无状态**：服务器不需要存任何东西，Token 自带用户信息
- **跨服务器**：任何服务器都能验证同一个 Token
- **前后端分离友好**：放在 Header 里，不依赖 Cookie

### 2.3 JWT 的结构

JWT 由三部分组成，用 `.` 分隔：

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhZG1pbiIsImlhdCI6MTcxMH0.signature
|____Header____|.______Payload______|.___Signature___|
```

- **Header**：算法信息（如 HS256）
- **Payload**：用户数据（如用户名、过期时间），Base64 编码（不是加密！）
- **Signature**：签名 = Header + Payload + 密钥，防篡改

**重要**：Payload 是 Base64 编码，不是加密！任何人都能解码看到内容。所以**不要在 JWT 里放密码等敏感信息**。

## 三、Spring Security 基本概念

Spring Security 是 Spring 生态的安全框架，处理认证和授权。

### 3.1 过滤器链

Spring Security 的核心是一系列**过滤器（Filter）**，请求进来后依次经过：

```
请求 → Filter1 → Filter2 → ... → Controller
              ↓
        认证失败？→ 返回 401
        权限不足？→ 返回 403
```

我们要做的就是在过滤器链中加入自己的 JWT 过滤器。

### 3.2 SecurityFilterChain

通过配置 `SecurityFilterChain` 来定义安全规则：
- 哪些路径不需要认证（如登录接口）
- 哪些路径需要认证
- 使用什么认证方式

### 4.2 JwtUtil 工具类

负责 Token 的生成和解析：

```java
@Component
public class JwtUtil {

    // 密钥（生产环境放配置文件，不要硬编码）
    private static final String SECRET = "my-secret-key-for-jwt-which-needs-to-be-at-least-256-bits-long!!";
    // 过期时间：24 小时
    private static final long EXPIRATION = 24 * 60 * 60 * 1000;

    private SecretKey getSigningKey() {
        return Keys.hmacShaKeyFor(SECRET.getBytes(StandardCharsets.UTF_8));
    }

    // 生成 Token
    public String generateToken(String username) {
        return Jwts.builder()
                .subject(username)
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + EXPIRATION))
                .signWith(getSigningKey())
                .compact();
    }

    // 从 Token 中获取用户名
    public String getUsernameFromToken(String token) {
        return getClaims(token).getSubject();
    }

    // 验证 Token 是否有效
    public boolean validateToken(String token) {
        try {
            getClaims(token);
            return true;
        } catch (Exception e) {
            return false;
        }
    }

    private Claims getClaims(String token) {
        return Jwts.parser()
                .verifyWith(getSigningKey())
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }
}
```

### 4.5 Security 配置

```java
@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) {
        http
            .csrf(csrf -> csrf.disable())          // 前后端分离不需要 CSRF
            .sessionManagement(session ->
                session.sessionCreationPolicy(STATELESS))  // 无状态
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()    // 登录接口放行
                .anyRequest().authenticated()               // 其他都要认证
            )
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

### 4.6 完整认证流程

```
登录：
  POST /auth/login {username, password}
    → 验证通过 → 返回 {token: "eyJhbG..."}

访问受保护接口：
  GET /users/me
  Header: Authorization: Bearer eyJhbG...
    → JwtAuthenticationFilter 拦截
    → 解析 Token，获取用户名
    → 设置 SecurityContext
    → Controller 正常执行

未携带 Token：
  GET /users/me （无 Header）
    → 返回 401 Unauthorized
```

## 五、获取当前登录用户

在 Controller 中获取当前登录用户：

```java
@GetMapping("/users/me")
public Result<String> me(@AuthenticationPrincipal UserDetails userDetails) {
    return Result.success("当前用户：" + userDetails.getUsername());
}
```

也可以通过 `SecurityContextHolder` 获取：
```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String username = auth.getName();
```

## 六、JWT 的注意事项

1. **密钥要够长**：HS256 要求至少 256 位（32 字节）
2. **不要在 Payload 放敏感信息**：Payload 只是 Base64 编码，不是加密
3. **设置合理的过期时间**：太长不安全，太短用户体验差
4. **密钥不要硬编码**：放在配置文件或环境变量里
5. **Token 无法主动失效**：一旦签发，在过期前一直有效。要实现「踢下线」需要额外方案（如 Redis 黑名单）

### 练习 2：思考题

1. JWT 和 Session 认证的核心区别是什么？
2. 为什么前后端分离项目更适合用 JWT？
3. JWT 的 Payload 能放密码吗？为什么？
4. 如果要实现「修改密码后旧 Token 失效」，该怎么做？

**答案**：

1. 核心区别是**状态存储位置**。Session 把用户状态存在服务器内存（有状态），JWT 把用户信息编码在 Token 中由客户端携带（无状态）。Session 需要服务器记住每个用户，JWT 服务器不需要存任何东西。

2. 前后端分离项目中，前端和后端可能不同域名（跨域），Cookie 有同源限制不方便传递。JWT 放在请求 Header 里，不依赖 Cookie，天然支持跨域。同时移动端（App、小程序）也没有 Cookie 机制，JWT 更通用。

3. **绝对不能**。JWT 的 Payload 只是 Base64 编码，不是加密，任何人拿到 Token 都能解码看到 Payload 的内容。密码等敏感信息放进去等于明文泄露。

4. 在 Redis 中维护一个 Token 黑名单（或版本号）。用户修改密码时，把旧 Token 加入黑名单（或递增该用户的 Token 版本号）。JWT 过滤器验证时除了验签名和过期时间，还要检查 Redis 中该 Token 是否在黑名单中。
