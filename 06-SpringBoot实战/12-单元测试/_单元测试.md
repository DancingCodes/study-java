# 单元测试

## 一、为什么需要单元测试

到目前为止，我们测试接口都是启动项目后用 HTTP Client 或 Postman 手动发请求。这种方式有几个问题：

- **慢**：每次都要启动整个项目
- **不可重复**：数据库状态变了，结果可能不一样
- **覆盖不全**：边界情况、异常路径很容易漏测
- **回归困难**：改了一个地方，不知道有没有影响别的功能

单元测试 = **用代码测试代码**。写一次，永远可以一键运行，几秒钟就能验证所有逻辑。

```
手动测试：启动项目 → 打开浏览器 → 发请求 → 看结果 → 改代码 → 重启 → 再测...
单元测试：写好测试 → 点一下运行 → 全部通过 ✅（几秒钟）
```

企业项目中，单元测试是代码质量的保障。没有测试的代码，改起来提心吊胆。

## 二、JUnit 5 基础

JUnit 5 是 Java 最主流的测试框架，Spring Boot 已经内置（`spring-boot-starter-test` 包含了 JUnit 5）。

### 2.1 第一个测试

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {

    @Test
    void testAdd() {
        int result = 1 + 1;
        assertEquals(2, result);  // 期望值, 实际值
    }
}
```

- `@Test` 标记一个测试方法
- `assertEquals(expected, actual)` 断言期望值等于实际值
- 测试方法不需要 `public`，JUnit 5 支持包级别访问

### 2.2 常用断言方法

| 方法 | 作用 | 示例 |
|------|------|------|
| `assertEquals(expected, actual)` | 相等 | `assertEquals(3, 1+2)` |
| `assertNotEquals(a, b)` | 不相等 | `assertNotEquals(0, 1)` |
| `assertTrue(condition)` | 为真 | `assertTrue(list.isEmpty())` |
| `assertFalse(condition)` | 为假 | `assertFalse(name.isBlank())` |
| `assertNull(obj)` | 为 null | `assertNull(result)` |
| `assertNotNull(obj)` | 不为 null | `assertNotNull(user)` |
| `assertThrows(异常类, 代码块)` | 抛指定异常 | `assertThrows(BusinessException.class, () -> service.getById(999L))` |

`assertThrows` 是测试异常路径的利器：

```java
@Test
void testGetByIdNotFound() {
    // 期望抛出 BusinessException
    BusinessException ex = assertThrows(BusinessException.class, () -> {
        productService.getProductById(999L);
    });
    assertEquals("商品不存在", ex.getMessage());
}
```

### 2.3 生命周期注解

```java
import org.junit.jupiter.api.*;

class LifecycleTest {

    @BeforeAll
    static void beforeAll() {
        // 所有测试前执行一次（初始化资源）
    }

    @BeforeEach
    void beforeEach() {
        // 每个测试方法前执行（重置状态）
    }

    @Test
    void test1() { ... }

    @Test
    void test2() { ... }

    @AfterEach
    void afterEach() {
        // 每个测试方法后执行（清理）
    }

    @AfterAll
    static void afterAll() {
        // 所有测试后执行一次（释放资源）
    }
}
```

## 三、Mockito — 模拟依赖

### 3.1 为什么需要 Mock

Service 层依赖 Mapper（数据库操作）。如果测试 Service 时真的去查数据库：
- 需要启动数据库
- 数据不稳定（别人改了数据，测试就挂了）
- 速度慢

Mock（模拟）= 创建一个假的 Mapper，你可以控制它返回什么数据。这样就能只测试 Service 的业务逻辑，不依赖数据库。

### 3.2 基本用法

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.mockito.Mockito.*;
import static org.junit.jupiter.api.Assertions.*;

@ExtendWith(MockitoExtension.class)  // 启用 Mockito
class ProductServiceTest {

    @Mock
    private ProductMapper productMapper;  // 创建假的 Mapper

    @InjectMocks
    private ProductServiceImpl productService;  // 把假 Mapper 注入到 Service

    @Test
    void testGetById() {
        // 1. 设定：当调用 mapper.selectById(1L) 时，返回一个模拟的商品
        Product mockProduct = new Product(1L, "手机", 2999.0, 100);
        when(productMapper.selectById(1L)).thenReturn(mockProduct);

        // 2. 执行：调用 Service 方法
        Product result = productService.getProductById(1L);

        // 3. 验证：结果是否正确
        assertNotNull(result);
        assertEquals("手机", result.getName());
        assertEquals(2999.0, result.getPrice());

        // 4. 验证：mapper.selectById 是否被调用了一次
        verify(productMapper, times(1)).selectById(1L);
    }
}
```

### 3.3 Mockito 三步走

```
1. when(...).thenReturn(...)  — 设定假数据
2. 调用被测方法                — 执行
3. assert / verify            — 验证结果和行为
```

### 3.4 常用 Mockito 方法

| 方法 | 作用 |
|------|------|
| `when(mock.method()).thenReturn(value)` | 设定返回值 |
| `when(mock.method()).thenThrow(exception)` | 设定抛异常 |
| `verify(mock).method()` | 验证方法被调用过 |
| `verify(mock, times(n)).method()` | 验证调用了 n 次 |
| `verify(mock, never()).method()` | 验证从未调用过 |
| `any()` / `anyLong()` / `anyString()` | 匹配任意参数 |

## 四、@SpringBootTest — 集成测试

单元测试用 Mock 隔离依赖，速度快。但有时你需要测试整个流程（Controller → Service → Mapper），这时用 `@SpringBootTest` 启动完整的 Spring 容器：

```java
@SpringBootTest
class ProductServiceIntegrationTest {

    @Autowired
    private ProductService productService;

    @Test
    void testList() {
        // 这里会真正调用数据库
        List<Product> products = productService.list();
        assertNotNull(products);
    }
}
```

**单元测试 vs 集成测试**：

| | 单元测试 | 集成测试 |
|---|---------|----------|
| 注解 | `@ExtendWith(MockitoExtension.class)` | `@SpringBootTest` |
| 依赖 | Mock 模拟 | 真实依赖 |
| 速度 | 毫秒级 | 秒级（启动 Spring 容器） |
| 用途 | 测试单个方法的逻辑 | 测试完整流程 |
| 推荐比例 | 多 | 少 |

日常开发以单元测试为主，关键流程补充集成测试。

## 五、MockMvc — Controller 层测试

MockMvc 可以模拟 HTTP 请求，不需要真正启动 Tomcat：

```java
import org.springframework.test.web.servlet.MockMvc;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest
@AutoConfigureMockMvc
class ProductControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void testGetById() throws Exception {
        mockMvc.perform(get("/products/1"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.code").value(200))
               .andExpect(jsonPath("$.data.name").exists());
    }

    @Test
    void testCreate() throws Exception {
        String json = "{\"name\":\"测试商品\",\"price\":99.0,\"stock\":10}";

        mockMvc.perform(post("/products")
                       .contentType("application/json")
                       .content(json))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.code").value(200));
    }
}
```

`jsonPath` 用来检查 JSON 响应中的字段，语法类似 XPath：
- `$.code` — 根对象的 code 字段
- `$.data.name` — data 对象的 name 字段
- `$.data[0].name` — data 数组第一个元素的 name

## 六、测试覆盖率

测试覆盖率 = 被测试执行过的代码行数 / 总代码行数。

- IDEA 自带覆盖率工具：右键测试类 → Run with Coverage
- 一般要求：核心业务代码覆盖率 > 80%
- 覆盖率不是越高越好，100% 覆盖率不代表没有 Bug

重点覆盖：
- 正常路径（happy path）
- 异常路径（参数为空、数据不存在、业务规则不满足）
- 边界条件（空列表、最大值、最小值）

## 七、测试最佳实践

1. **测试方法命名**：`test + 场景 + 预期结果`，如 `testGetByIdWhenNotFoundThenThrowException`
2. **一个测试方法只测一件事**：不要在一个方法里测 5 个场景
3. **AAA 模式**：Arrange（准备数据）→ Act（执行）→ Assert（验证）
4. **测试要独立**：每个测试不依赖其他测试的运行顺序或结果
5. **先写测试再写代码**（TDD）：高级做法，了解即可

## 练习

### 练习 1：给 ProductService 写单元测试

测试以下场景：
1. `getProductById` — 正常查询，返回商品
2. `getProductById` — 商品不存在，抛 BusinessException
3. `createProduct` — 正常创建，调用 mapper.insert

**答案**：已在 `test-demo/src/test/java/com/study/testdemo/service/ProductServiceTest.java` 中实现：

```java
@ExtendWith(MockitoExtension.class)
class ProductServiceTest {

    @Mock
    private ProductMapper productMapper;

    @InjectMocks
    private ProductServiceImpl productService;

    @Test
    void testGetProductByIdSuccess() {
        Product mockProduct = new Product(1L, "手机", 2999.0, 100);
        when(productMapper.selectById(1L)).thenReturn(mockProduct);
        Product result = productService.getProductById(1L);
        assertNotNull(result);
        assertEquals("手机", result.getName());
        verify(productMapper, times(1)).selectById(1L);
    }

    @Test
    void testGetProductByIdNotFound() {
        when(productMapper.selectById(999L)).thenReturn(null);
        BusinessException ex = assertThrows(BusinessException.class, () -> {
            productService.getProductById(999L);
        });
        assertEquals(404, ex.getCode());
        assertEquals("商品不存在", ex.getMessage());
    }

    @Test
    void testCreateProduct() {
        Product newProduct = new Product(null, "笔记本电脑", 5999.0, 50);
        when(productMapper.insert(newProduct)).thenReturn(1);
        Product result = productService.createProduct(newProduct);
        assertNotNull(result);
        verify(productMapper, times(1)).insert(newProduct);
    }
}
```

### 练习 2：思考题

1. 单元测试和集成测试的区别是什么？各适合什么场景？
2. 为什么要用 Mock 而不是真的去查数据库？
3. `@Mock` 和 `@InjectMocks` 分别做了什么？

**答案**：

1. **单元测试**用 `@ExtendWith(MockitoExtension.class)` + Mock 隔离依赖，只测单个方法的业务逻辑，毫秒级速度，适合日常开发频繁运行。**集成测试**用 `@SpringBootTest` 启动完整 Spring 容器，测试 Controller → Service → Mapper 的完整流程，秒级速度，适合验证关键流程端到端的正确性。日常开发以单元测试为主，关键流程补充集成测试。

2. 真的查数据库有三个问题：①需要启动数据库，环境依赖重；②数据不稳定，别人改了数据测试就挂；③速度慢。Mock 创建假的 Mapper，你可以完全控制它返回什么数据，测试稳定、可重复、速度快，只专注于 Service 的业务逻辑。

3. `@Mock` 创建一个假对象（模拟的依赖），你可以用 `when().thenReturn()` 控制它的返回值。`@InjectMocks` 创建被测试类的真实实例，并自动把 `@Mock` 创建的假对象注入到它的依赖字段中。这样被测试类执行真实逻辑，但它依赖的对象是假的。
