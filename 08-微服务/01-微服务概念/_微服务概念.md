# 微服务概念

## 一、单体架构 vs 微服务架构

### 1.1 单体架构

所有功能模块打包在一个应用中，部署在一台服务器上：

```
一个 jar/war
├── 用户模块
├── 商品模块
├── 订单模块
├── 支付模块
└── 通知模块
```

**优点**：
- 开发简单，一个项目搞定
- 部署简单，一个 jar 包
- 调用方便，直接方法调用

**缺点**：
- 代码量大了以后难以维护
- 一个模块出 bug 可能拖垮整个系统
- 无法针对某个模块单独扩容（订单量大，只能整体扩容）
- 技术栈绑定，所有模块必须用同一套

### 1.2 微服务架构

将应用拆分成多个**小的、独立部署的服务**，每个服务负责一个业务功能：

```
用户服务（独立部署，独立数据库）
商品服务（独立部署，独立数据库）
订单服务（独立部署，独立数据库）
支付服务（独立部署，独立数据库）
通知服务（独立部署，独立数据库）
```

服务之间通过 **HTTP / RPC** 通信。

**优点**：
- 每个服务独立开发、部署、扩容
- 技术栈灵活，不同服务可以用不同语言
- 故障隔离，一个服务挂了不影响其他
- 团队独立，每个团队负责自己的服务

**缺点**：
- 运维复杂度大幅增加
- 服务间通信有网络开销
- 分布式事务难处理
- 需要服务治理（注册发现、熔断、限流等）

### 1.3 什么时候用微服务？

| 场景 | 建议 |
|------|------|
| 小团队（1-5 人）、业务简单 | 单体架构 |
| 中等规模、业务增长中 | 单体 → 逐步拆分 |
| 大团队、业务复杂、高并发 | 微服务架构 |

**核心原则**：不要为了微服务而微服务。先用单体快速上线，业务复杂了再拆。

## 二、微服务技术栈

### 2.1 Spring Cloud 全家桶

Spring Cloud 是一套微服务解决方案，提供了服务治理的各种组件：

| 功能 | 组件 | 说明 |
|------|------|------|
| 注册中心 | **Nacos** | 服务注册与发现、配置中心 |
| 远程调用 | **OpenFeign** | 声明式 HTTP 客户端 |
| 网关 | **Gateway** | 统一入口、路由、鉴权、限流 |
| 熔断降级 | **Sentinel** | 流量控制、熔断保护 |
| 分布式事务 | **Seata** | 跨服务事务一致性 |
| 配置中心 | **Nacos**（兼任） | 统一管理配置，动态刷新 |

### 2.2 微服务通信方式

| 方式 | 协议 | 特点 | 代表 |
|------|------|------|------|
| HTTP REST | HTTP | 简单通用，跨语言 | OpenFeign、RestTemplate |
| RPC | TCP | 性能高，二进制传输 | Dubbo、gRPC |
| 消息队列 | AMQP 等 | 异步解耦 | RabbitMQ、Kafka |

本阶段学习 HTTP REST 方式（OpenFeign），这是 Spring Cloud 的主流方案。

### 2.3 微服务架构全景图

```
                    客户端（浏览器/App）
                          ↓
                    ┌─────────────┐
                    │   Gateway   │  ← 网关：路由、鉴权、限流
                    └──────┬──────┘
               ┌───────────┼───────────┐
               ↓           ↓           ↓
          用户服务      商品服务     订单服务    ← 各服务独立部署
               ↑           ↑           ↑
               └───────────┼───────────┘
                    ┌──────┴──────┐
                    │    Nacos    │  ← 注册中心 + 配置中心
                    └─────────────┘
```

每个服务启动时向 Nacos 注册自己，调用其他服务时从 Nacos 获取地址。

## 三、服务拆分原则

### 3.1 怎么拆？

1. **按业务领域拆**：用户、商品、订单、支付、通知各一个服务
2. **单一职责**：每个服务只做一件事
3. **高内聚低耦合**：服务内部紧密关联，服务之间尽量少依赖
4. **独立数据库**：每个服务有自己的数据库，不直接访问别人的库

### 3.2 拆分粒度

| 粒度 | 说明 | 问题 |
|------|------|------|
| 太粗 | 几个大服务，和单体差不多 | 拆了等于没拆 |
| 太细 | 每个接口一个服务 | 运维爆炸，调用链过长 |
| 合适 | 按业务边界，3-10 个服务起步 | 逐步拆分 |

### 3.3 拆分后的挑战

| 挑战 | 解决方案 |
|------|----------|
| 服务怎么找到彼此？ | 注册中心（Nacos） |
| 服务间怎么调用？ | 远程调用（OpenFeign） |
| 某个服务挂了怎么办？ | 熔断降级（Sentinel） |
| 统一入口怎么处理？ | 网关（Gateway） |
| 跨服务的事务怎么保证？ | 分布式事务（Seata） |
| 配置怎么统一管理？ | 配置中心（Nacos） |

## 四、本阶段学习路线

```
微服务概念（本课）
    ↓
Nacos 注册中心（服务注册与发现）
    ↓
OpenFeign（服务间调用）
    ↓
Gateway（统一网关）
    ↓
Sentinel（熔断降级）
    ↓
Seata（分布式事务）
```

我们会用一个简化版的电商场景贯穿整个阶段：用户服务 + 商品服务 + 订单服务。
